# Decisions

Status: **Accepted** (in force) · **Proposed** (recommended by the audit; confirm or amend in the named
phase) · **Open** (needs the owner; don't invent an answer).

## Accepted

| ID    | Decision                                                                                                                                  | Rationale / rejected alternatives                                                                                    |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| A-001 | One modular product with adaptive complexity for kirana, medium grocery and supermarket.                                                  | Owner direction. Rejected: separate products per segment.                                                            |
| A-002 | One store per business in the MVP; the data model is store-aware (`storeId` on store-owned records). No multi-store workflows.             | Owner direction. Keeps multi-store possible without building it.                                                     |
| A-003 | PostgreSQL is authoritative for online transactions; desktop offline writes are durable in SQLite and sync through a durable outbox.      | Owner direction.                                                                                                     |
| A-004 | Stock is ledger-based: append-only movements with source, actor, timestamp and reason/reference.                                         | Owner direction. Rejected: editable stock balance fields (what the current `inventory` column is).                   |
| A-005 | Completed sales, payments and customer/supplier ledger entries are immutable; corrections use returns, reversals or audited adjustments. | Owner direction. Rejected: the current update/delete of orders.                                                      |
| A-006 | Decimal-safe money; price/tax snapshots on completed transactions; profit needs a defined cost basis and returns handling.                | Owner direction. Rejected: the current `Float` money columns.                                                        |
| A-007 | A displayed UPI QR is not proof of payment. "UPI recorded" (manual) and "UPI confirmed" (trusted gateway) are distinct states.            | Owner direction.                                                                                                     |
| A-008 | Tenant and role permissions are enforced on the backend.                                                                                  | Owner direction.                                                                                                     |
| A-009 | OCR/AI output never posts purchases, payments or financial entries without human approval.                                               | Owner direction.                                                                                                     |
| A-010 | India/INR defaults; tax and invoice settings configurable; GST registration never assumed; tax rules validated before they're built.      | Owner direction.                                                                                                     |
| A-011 | Keep the existing backend stack: Node, Express 5, TypeScript, Prisma 5, PostgreSQL, zod, and the current layering and conventions.       | It is sound and small. Rejected: rewriting in NestJS or another framework, or swapping the ORM. Revisit the Prisma 5 → 6+ upgrade separately, not mid-phase. |
| A-012 | Durable project memory lives in the backend repo (`Kirana-B`): `CLAUDE.md` + `docs/`. The workspace root and each client repo get a short pointer `CLAUDE.md` plus repo-specific notes only. | The backend owns the business rules and every phase touches it. Rejected: copies of the docs in every repo (they drift). |
| A-013 | Separate repos (owner, 2026-11-16): `Kirana-B` backend API, `kirana-F` web admin, `Kirana-app` Android, and `Kirana-desktop` Windows POS. | Owner decision. Rejected: a monorepo (the former P-008). Consequence: a cross-repo API contract is needed (new P-008). |
| A-014 | `github.com/SMulla786/Kirana-B` replaces `kirana-backend` as the backend repo. Done locally 2026-11-16: the owner moved the old `nk-B` files into `Kirana-B` without git history; old code may be reused or changed as needed. | Owner decision, 2026-11-16. |
| A-015 | (was P-001) `kirana` stays the Business/tenant model. `Store` exists, and one default store is created atomically with the business. `Session.storeId` carries the store; there are no multi-store workflows. | Built in Phase 1A. Rejected: renaming tables (churn). |
| A-016 | (was P-003) Tests use Vitest + supertest against a real Postgres `*_test` database, created via `prisma db push`. CI runs typecheck, lint and tests on GitHub Actions. | Built in 1A. A test DB, not mocks, because tenant and ledger rules need real queries. |
| A-017 | (was P-004) `Membership(userId, kiranaId, role)` with OWNER/MANAGER/CASHIER/INVENTORY_MANAGER/ACCOUNTANT/STAFF; a code-defined role → permission map (`src/config/permissions.ts`); `requirePermission`. Only OWNER grants MANAGER; nobody grants OWNER through the API. Platform ADMIN stays on `User.role`. The legacy `employee` table is left in place but unused. | Built in 1A. Migration backfills kirana owners as OWNER and employees as STAFF. |
| A-018 | (was P-005) Auth: HS256 access JWT `{sub, sid, typ:'access'}` (≤60 min, default 15) checked against a live `Session` on every request. The opaque refresh token `<sessionId>.<secret>` is stored as a SHA-256 hash, rotated on each refresh, and reuse revokes the session. Reset tokens are single-use and hashed. Verify codes come from `crypto.randomInt`. Login errors are uniform. Auth rate limits are mounted. Public registration never accepts a role. | Built in 1A. Deferred: cashier PIN login (needs POS device registration, Phase 3/9) and per-account lockout. |
| A-019 | (was P-007) Dead template exports and unused S3/Cloudinary/multer/regression helpers were deleted, not stubbed. | Done in 1A (commits `7dcda39`, `e6c9ce0`). |
| A-020 | (was P-010) Phase 1 is split into 1A (backend) and 1B (clients). The owner chose to build the `kirana-F` web shell alongside 1A; desktop and Android shells wait. | Owner, 2026-11-16. |
| A-021 | (O-5, O-12) Shops are onboarded both by self-signup (`POST /auth/register`, email-verified) and by platform admin (`POST /admin/businesses`, pre-verified). Login is email-or-username + password; email verification stays. | Owner, 2026-11-16. `kirana.amount`/`renewalAmount` default to 0; their billing meaning is still open (O-5). Phone OTP is not planned for now. |
| A-022 | Web UI visual direction (owner, 2026-11-16): the whole `kirana-F` app follows the style of the Dribbble shot "GeoSales" (https://dribbble.com/shots/26730948). Dark charcoal surfaces with lighter hairline-bordered cards (~16px radius); lime-green primary, amber secondary, muted red for negatives; small muted labels with bold tabular KPI numbers and delta pills (icon + text); card headers with an action icon. | Style reference only, never copied. Accessibility still rules: contrast >= 4.5:1, focus rings, 44px targets. Desktop keeps a labelled sidebar for shopkeepers. Placeholders never show fake numbers. |
